# Windows local-user command overlap and output

## Goal

While one protected command is running, a second command in the same workspace can finish without waiting for the first. stdout/stderr must be observable before termination. Retain per-command identity, filesystem and network enforcement, process-tree containment, cancellation, and explicit cleanup errors. The previous temporary-account implementation left loaded profiles after scheduled tasks; test account deletion separately from SID-bound profile unload/removal and do not ship unbounded profile growth.

## Design constraints

- The elevated runner currently reuses one local account, resetting its password and enabling/disabling it around each run. Its ordinary SID is also the target of filesystem deny entries and outbound firewall rules. Concurrent jobs need independently owned ordinary identities as well as capability SIDs; otherwise shortening the lock can mix deny policies, network modes, and account teardown. Preserve installation/preflight behavior and define account cleanup after process-tree termination, including failed setup.
- Keep the existing cross-process exclusion while filesystem policy changes are applied or reversed. Do not shorten lock lifetime until rollback removes only the current invocation's changes; restoring a whole DACL would overwrite other live changes. Account for inherited grants, null DACLs and failed setup. A CWD-keyed lock cannot cover shared ancestors.
- Leave already-installed versions, ordinary-user AppContainer isolation, the public API and other OS backends unchanged. Evaluate interaction with AppContainer ACL writers before altering shared ACL coordination.
- Follow the existing protected task transport's raw stdout and stderr files using independent byte offsets. Final drain must not duplicate bytes or wait for new output and must preserve task exit and cancellation semantics.

## Validation

- Unit: output appends by offset, exact binary bytes including partial UTF-8 chunks, absent and empty files, final drain.
- Native Windows: hold a protected long command behind a file gate, finish a short command in that workspace first, then release the long command and verify its write access. Verify background output before release, process-tree cancellation and no stale task/rules/grants.
- Exercise overlap and cleanup in both orders, shared ancestors, failure rollback and deny policies; run existing Windows filesystem/network integration coverage before release.

## Status

The same-workspace regression on Windows 11 (interactive, elevated process) failed against the unchanged dependency: the long job started and the short command reached its execution timeout before the release file was present. The output-only candidate passed the local cursor race test and the native workspace test for observing live child output and killing its process tree. The first overlap candidate cross-compiled but failed before the long job's start marker. Job status proved the legacy `net user` password-length confirmation rejected unattended account creation. Creating the per-run account through `NetUserAdd` resolved startup: the same native regression passed in 9.68 seconds and the long job still wrote after the short one ended. The resulting two per-run Windows profiles remained loaded after their accounts, tasks, firewall entries, and visible processes were gone. This matches the historical reason the backend switched to a stable account. Both ACL cleanup orders and ancestor DACL tests passed on native Windows, including preservation of the still-running invocation's entry. Waiting for a terminal scheduler action before deleting its task, then attempting `DeleteProfileW` for that exact SID, still failed on Windows with a sharing violation. A completed scheduler action is not sufficient proof that its user profile is unloaded. Delayed inventory still showed four loaded probe profiles and no corresponding local accounts, so delayed account deletion alone cannot bound resource use. A standalone profile-free `CreateProcessWithLogonW` probe in Windows session 0 produced the expected exit code for `cmd.exe` and no profile for its disposable SID. The same launch with PowerShell exited `0xC0000142` and also produced no profile. The interactive PowerShell probe did work without loading a profile. Changing console flags alone did not fix session 0. With a dedicated noninteractive window station and desktop whose ACL grants access only to the host caller and the disposable account SID, the session-0 PowerShell probe returned exit 37 and created no profile. This isolates the startup problem without changing the shared service desktop.

## Before publication

- Put private window-station creation and any process-wide station switch in the existing single-invocation controller process, not in the shared host. Use profile-free account logon for the trusted broker. Keep the protected transport and the broker's restricted token and process-tree Job Object for business commands.
- Ensure the host can cancel and reap the broker even when the controller is interrupted. Do not run the business command directly under the probe's ordinary account token, and do not fall back to the scheduler path that creates per-invocation profiles.
- Validate normal exit, cancellation, and setup failure under session 0 and interactive hosts. Inventory every generated SID's profile, firewall rule, and account before/after; require no unmatched entries. Run overlapping file and network policy checks and the downstream background lifecycle against the same candidate. The profile-free candidate closed the observed profile lifecycle gap on the tested native host; publication still requires validation of the final revision and durable lifecycle tests. Do not reuse an account SID unless cleanup can prove the preceding job's grants cannot affect its successor. A candidate must also pass the existing cancellation and filesystem/network isolation suite as one combined build.

## Final review follow-up

Removed unused batch logon grants from invocation setup, made failed setup/prepare return rollback errors, and zeroed the temporary UTF-16 password buffer. Local-user filesystem updates now take the existing same-user AppContainer ACL lock in addition to the backend setup lock; null-DACL replacement retains both through rollback. Broker termination waits for its Job Object active process count to reach zero before reversing host policy. Added a gated upstream integration test for live stdout/stderr, same-directory commands with independent read/write policies, both open/offline ordering combinations, exact final output, and baseline resource inventory (accounts, profiles, firewall rules, transport directories). The broker now receives an explicit system environment block; a native regression checks that controller credentials and host-only variables do not reach the business command while requested variables remain available. The final candidate passed the new environment and overlap regressions in both elevated session 0 and an interactive session. The native ACL suite also passed null-DACL restoration after multiple entries and cancellation while an AppContainer writer owns the ACL lock. Upstream lifecycle, filesystem, transport, bootstrap and downstream background completion/cancellation tests passed. One early scheduler probe left an inactive task and made the global cleanup audit fail; after verifying its exact legacy action and removing that task, the unchanged cleanup audit passed. The Go TLS allowlist variant passed again against this same candidate. The canonical curl/Schannel test was rerun against the final candidate and still failed with exit 35 / SEC_E_NO_CREDENTIALS after CONNECT in both variants. The same failure was reproduced earlier against the pinned unmodified dependency on this native host. This remains an explicit Windows curl compatibility limitation; the Go TLS variant proves policy enforcement for that client only. The original candidate was published as upstream PR #12 and merged; the password-policy follow-up below records the hosted CI gap.

## Password-policy follow-up

The overlap change was merged in upstream PR #12. Both its PR check and the merged main push failed before command launch: `NetUserAdd` returned 2245 for every invocation account. A native comparison reproduced the failure with `PasswordComplexity=1`; the original test host had this setting disabled. The API defaults the display name to `sbx-<random>`, and Windows splits display names on hyphens when rejecting password tokens. The fixed `Sbx!` password prefix therefore fails the case-insensitive `sbx` check. An independent password prefix passed on the same host. The probe restored the original policy and deleted its exact accounts.

Use an independent prefix and four eight-character random groups so neither display-name token can occur, even with repetitive random input. Password entropy remains 128 bits. Deterministic credential tests cover character classes, length and token exclusion; the existing invocation CI selector also exercises actual account creation with the host's unchanged effective policy. Repeat the CI execution selectors under enabled complexity on the native test host, then restore its original setting. The hosted Windows runner remains the final compatibility check.

Validation: `make ci`, Windows vet and cross-compilation passed. On native Windows with complexity enabled, the backend CI selectors passed ten repetitions and all execution CI selectors passed three repetitions, including overlap, independent policies, environment isolation and lifecycle cleanup. The policy restoration completed successfully. No CI selector or machine-policy relaxation is part of the patch.
